Записи по итогам анализа проекта (2026-09-29). Разделы: срочное (риски),
качество/производительность, архитектура, UX, гигиена репозитория, идеи на

## P0 — Данные и корректность

### 0.1. Защита от необратимой потери сессий при битом JSON
`SessionCodec.decode` при ошибке парсинга возвращает `emptyList()`
(`SessionCodec.kt:32`). Следующий `save()` перезапишет хранилище пустым
списком — все сессии пропадут безвозвратно.

Идеи:
- Различать «пусто» и «не удалось распознать»: `decode` возвращает
  `Result`/ sealed-типа, репозиторий логирует ошибку и **не перезаписывает**
  ключ до успешного чтения.
- При старте приложения — разовая проверка «починенного» бэкапа
  (копия исходной строки в отдельный ключ) + диалог восстановления.
- Как минимум: `Log.e` с длиной нераспознанной строки, чтобы падение
  диагностировалось.

### 0.2. `clearNumbers` нарушает контракт сортировки
`DataStoreSessionRepository.clearNumbers` (`DataStoreSessionRepository.kt:71-74`)
не пересортировывает список, а `InMemorySessionRepository` — пересортировывает
(`InMemorySessionRepository.kt:45`). После сброса чисел порядок на Home
становится произвольным.

Идея: единая приватная функция `merge(list, session)` в обоих репозиториях
(или вынести в `SessionRepository`-расширение), чтобы правила не расходились.
Хорошо ловится общим контрактным тестом на оба репозитория
(один и тот же набор кейсов, параметризованный).

### 0.3. Гонки записи в `SessionViewModel`
`generate()` захватывает `session` до `update`, а сохранение уходит в
отдельную корутину на каждый тап (`SessionViewModel.kt:106`, `:153`).
Быстрые повторные нажатия создают несколько «снимков» состояния, порядок
записи не гарантирован — часть чисел может потеряться.

Идеи (по возрастанию сложности):
- `Mutex` в VM вокруг «посчитать → применить → сохранить».
- Единая очередь операций: `Channel<Command>` + один обработчик в
  `viewModelScope` (паттерн actor).
- Хранить не снимок `Session`, а `transform: (Session) -> Session`, который
  применяется к актуальному состоянию в момент записи.

### 0.4. `save()` воскрешает удалённую сессию
`DataStoreSessionRepository.save` делает `filterNot { id == }` + добавление
(`DataStoreSessionRepository.kt:46`). Если сессию удалили с другого экрана
(или из другого процесса/виджета), последующая генерация её вернёт.

Идея: `save` = upsert только для существующих; создание новой сессии —
отдельный `create(session)`, который падает/игнорируется при конфликте id.
Либо `save(session, expectExisting: Boolean)`.

## P1 — Производительность и утечки

### 1.1. `pickUnique` — линейный перебор диапазона — ✅ выполнено 2026-09-29
Было: два прохода `for (value in min..max)` при исчерпании «быстрых»
попыток — для диапазона 1..10 000 000 это миллионы итераций на нажатие.

Сделано: 128 быстрых бросков, затем случайный сдвиг
`random.nextLong(size)` и обход по кругу до первого свободного значения.
Сложность O(размер хвоста), а не O(размер диапазона). Размер диапазона
считается в `Long` (в `Int` переполняется).

### 1.2. `Session.pickedCount` пересчитывался на каждой рекомпозиции
Было: `generated.toSet().size` при каждом обращении, а обращается UI
на каждом кадре со списком истории.

Сделано 2026-09-29: `pickedCount`, `rangeSize` и `isExhausted` — `by lazy`
(`Session` неизменяем, значит пересчёт на экземпляр безопасен).

### 1.3. `ToneGenerator` не освобождался
Было: нативный ресурс без `release()`, ленивая инициализация без
синхронизации (`beep()` мог прийти с разных потоков).

Сделано 2026-09-29: `release()` в `FeedbackProvider` (вызывается из
`App.onTerminate()`), ленивая инициализация под `synchronized`,
`@Volatile` на флагах настроек.

### 1.4. Хранение сессий одной JSON-строкой
Было: `DataStoreSessionRepository` писал весь список сессий в один ключ —
каждая генерация = перепарсинг + перезапись всего списка вблизи лимита
Preferences (~1 МБ на ключ).

Сделано 2026-09-29: сессии пишутся по ключам `session_<id>`, список id —
отдельным ключом `sessions_index`; запись атомарна через `edit`. Старый
формат (`sessions_json`) читается и мигрируется при первой записи.
Переход на Room остаётся отдельной задачей, если упрёмся в объём
(пункт 5.4 — виджет/плитка, которым нужен быстрый доступ к последней
сессии).

## P2 — Домен и качество кода

### 2.1. `withGenerated` не валидировал диапазон — ✅ выполнено 2026-09-29
`Session.withGenerated(number/numbers, at)` не проверял `min <= n <= max`,
в отличие от `addManual`. Число вне диапазона попадало в историю и ломало
прогресс/исчерпание.

Сделано: `require(numbers.all { it in min..max })` в `withGenerated`
(с указанием первого некорректного значения в сообщении). Генератор
диапазон гарантирует, проверка — страховка на пути импорта/декодирования.

### 2.2. Состояние формы новой сессии было в композабле — ✅ выполнено 2026-09-29
`minText`/`maxText`/`withoutRepeats` жили в `NewSessionScreen` и терялись
при повороте экрана.

Сделано: состояние формы перенесено в `NewSessionViewModel`, экран
переписан и работает с `uiState`; навигация идёт по `createdSessionId`.

### 2.3. Структура данных для «без повторений» — не начато
Вместо `List<Int>` + `Set`-скан при каждом выборе — хранить
`BitSet`/очередь оставшихся значений рядом с сериализуемым `List<Int>`.

Оценка сейчас другая: после 1.1 `pickUnique` делает 128 быстрых бросков
и обход по кругу, то есть упирается в среднее, а не в худший случай.
`BitSet` даст выигрыш только на очень больших диапазонах (10^6+),
а рядом с ним придётся дублировать состояние и синхронизировать его
с журналом. Отложено до появления реальных жалоб на скорость.

### 2.4. Кириллица в именах API — ✅ выполнено 2026-09-29
`СлучайныеЧислаTheme` компилировался, но мешал grep/IDE.

Сделано: `RandomNumbersTheme` и `Theme.RandomNumbers`; обновлены Kotlin,
XML и `AndroidManifest.xml`. Кириллица осталась только в KDoc-комментариях
(это читаемо и полезно).

### 2.5. `applicationId` с регистром и подчёркиванием — ✅ выполнено 2026-09-29
`applicationId = "CodeSyS.Random_Number"` не прошёл бы публикацию в Play.

Сделано: `applicationId = "ru.codesys.randomnumber"`, обновлён тест
инструментов (`ExampleInstrumentedTest`). Пакеты исходников
`CodeSyS.Random_Number.*` оставлены: их переименование — отдельная задача
с обновлением всех импортов и не даёт выигрыша в публикации.

### 2.6. Нет статического анализа — ✅ выполнено 2026-09-29
Было только `kotlin.code.style=official`.

Сделано: `ktlint 14.2.0` (детект не подошёл — в системе JDK 27, а detekt
1.23.8 поддерживает максимум JDK 21), `.editorconfig` со стилем
`intellij_idea`, `ktlintCheck` подключён к `check`. Поднятая им же
заодно `lint` нашла два настоящих дефекта (см. 4.6).

### 2.7. Дублирование кода фабрик ViewModel — ✅ выполнено 2026-09-29
Было: четыре почти одинаковых объекта в `ViewModelFactories.kt`.

Сделано: декларативный `viewModelFactory { initializer { ... } }`
из `androidx.lifecycle.viewmodel`.

## P2 — UX и i18n

### 3.1. `partial` не показывался пользователю — ✅ выполнено 2026-09-29
`BatchGenerationResult.partial` корректно вычислялся, но UI нигде не
сообщал, что выдано меньше, чем запрошено.

Сделано: в `SessionUiState` добавлено `lastBatchPartial`, экран показывает
уведомление «Выдано N из M — диапазон исчерпан» с точными числами
(а не «частично»), плюс диалог «Все числа выбраны».

### 3.2. Недостижимая проверка в `NewSessionScreen` — ✅ выполнено 2026-09-29
Было: `min > Int.MAX_VALUE` после `toIntOrNull()` — проверка не могла
сработать никогда.

Сделано: проверки диапазона живут в валидации `NewSessionViewModel`
(сравнение `min`/`max` как `Int` между собой), недостижимых веток нет.

### 3.3. Формат даты на Home — ✅ выполнено 2026-09-29
Было: `SimpleDateFormat` в `remember` без ключа, формат строкой, локаль
`Locale.getDefault()`.

Сделано: `DateFormat.getDateTimeInstance()` (учётёт локаль и 12/24-часовой
формат системы), пересчёт при смене конфигурации.

### 3.4. История росла без ограничений — ✅ выполнено 2026-09-29
Было: `FlowRow` рендерил всю историю — для больших сессий UI тяжелел.

Сделано: постраничный показ (`HISTORY_PAGE` чисел, кнопка «показать ещё»),
список — на `LazyVerticalGrid`, позиции и меню сбрасываются при изменении
истории.

### 3.5. Доступность — ✅ выполнено 2026-09-29
Было: `BigNumberCard` и чипы истории имели `onClick = {}` — TalkBack
озвучивал «кнопка» без эффекта.

Сделано: пустые `onClick` убраны, оставлен только `onLongClick` (копирование),
добавлены `contentDescription` с числом и `semantics` для крупного числа
и диалога исчерпания.

### 3.6. Отклик при генерации — ✅ выполнено 2026-09-30
Было: `feedback?.onGenerated()` — один сигнал на весь батч, в том числе
на 10 чисел сразу, так что пользователь не считал выданное.

Сделано: `FeedbackProvider.onGenerated(count)` получает реальное число
выданных значений. По умолчанию сигнал по-прежнему один на батч, но
появилась настройка «Отклик на каждое число» (`AppSettings.feedbackPerNumber`),
при ней сигналы идут по одному на число с паузой 110 мс — без паузы они
слились бы в один неразличимый импульс, а `ToneGenerator` на том же потоке
просто перезапустил бы тон. Переключатель неактивен, если выключены и
вибрация, и звук.

Решение «кто решает, сколько сигналов» принято в сторону провайдера, а не
ViewModel: `SystemFeedbackProvider` уже подписан на `SettingsRepository`,
поэтому `SessionViewModel` не пришлось менять конструктор и поднимать
зависимость настроек.

### 4.6. Исправления, найденные статическим анализом — ✅ выполнено 2026-09-29
Первый же прогон `lint` дал 7 ошибок, из них 6 — реальные дефекты,
а не стилистика:

- `RandomSource.kt`: `SecureRandom.nextInt(from, until)` и
  `nextLong(from, until)` существуют только с Java 17 (Android API 35),
  а `minSdk = 24` — на старых устройствах это был бы `NoSuchMethodError`.
  Переписано на `nextInt(until)`/`nextLong()` с отбором по модулю;
  ширина диапазона считается в `Long` (в `Int` она переполняется).
  Добавлены тесты на широкие диапазоны и обе границы.
- `HomeScreen.kt` / `SessionScreen.kt`: `context.getString(...)` внутри
  snackbar-колбэков — `LocalContext` не реагирует на смену конфигурации,
  пользователь увидел бы текст прошлой локали. Заменено на
  `stringResource(...)` в момент композиции.

### 5.3. Seed для воспроизводимости — ✅ выполнено 2026-09-29
Было: идея. Сделано: `seed: Long?` в `Session` + `Random(seed)` через
`createRandom(mode, seed)`. Seed имеет приоритет над выбором источника
случайности (иначе «воспроизведение» было бы фикцией). Есть индикатор
и поле ввода на экране сессии.

### 5.4. Быстрый доступ из Home — ✅ выполнено 2026-10-05
Виджет/плитка/ярлыки (этап 3). Сделано: Glance-виджет `LatestSessionWidget`
(«последняя сессия» + кнопка «Сгенерировать»), плитка быстрых настроек
`QuickGenerateTileService`, статические ярлыки долгого нажатия по иконке
(«Новая сессия» / «Последняя сессия»). Общая логика генерации —
`platform/QuickGenerate`, поэтому виджет и плитка ведут себя одинаково.

Осталось (опционально, не начато): `observeLatestSession()` в репозитории,
чтобы не грузить весь список ради «последней сессии». Сейчас `QuickGenerate`
делает `observeSessionsOnce().firstOrNull()`. Возвращаться только если виджет
начнёт тормозить на холодном чтении — тогда и пересматривать Room (см. 1.4).

### 5.5. Режим «списка элементов» — ✅ выполнено 2026-10-03
Обобщение `Session` на «числа»/«элементы» (этап 2, задача 2.0). Сделано:

### 5.6. Логи генерации — ✅ выполнено 2026-09-29

Сделано: `log: List<GeneratedEntry(value, at)>`, `generated` стал

используются в экспорте CSV/JSON.
